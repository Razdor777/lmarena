# Обновление Juzdex на новую версию игры (пример: 1.21.70)

Коротко: обновить версию = заново снять **подписи** и **оффсеты** с нового
`Minecraft.Windows.exe` и поправить таблицы ID. Кода логики это не касается —
меняются только файлы ниже.

---

## 1. Что именно привязано к версии

| Файл | Что внутри | Сколько | Ломается при обновлении |
|---|---|---|---|
| `src/SDK/SigManager.hpp` | байтовые сигнатуры функций игры (`DEFINE_SIG`) | **124** | почти всегда — это основная работа |
| `src/SDK/OffsetProvider.hpp` | поля структур и индексы vtable (`DEFINE_INDEX_FIELD`, `DEFINE_INDEX_FIELD_TYPED`, `DEFINE_FIELD`) | **108** | частично: подпись ищет инструкцию, а из неё уже читается индекс/оффсет |
| `src/SDK/Minecraft/Actor/Components/ComponentHashes.hpp` | хэши имён ECS-компонентов | много | да, если Mojang добавил/переименовал компоненты (файл помечен «Last updated: 1.21.44») |
| `src/Features/Modules/Player/OreMinerV2.hpp` | runtime ID руд: 16/661 (уголь), 56/660 (алмаз), 129/662 (изумруд) | 6 | да — ID блоков сдвигаются при каждом контент-апдейте |
| `src/SDK/Minecraft/Network/PacketID.hpp` | ID пакетов (202 записи) | 202 | да, если добавили новый пакет в середину списка |
| `src/Utils/MiscUtils/ClientPack.cpp` | разбор игровых pack'ов (там есть пометки под 1.21.44) | — | только если менялся формат |
| `src/Hook/Hooks/NetworkHooks/PacketSendHook.cpp` | `vtable[2]` вручную | 1 | редко, но проверить |

Хуки, которые вешаются по `OffsetProvider` (`Actor_baseTick`,
`MinecraftUIRenderContext_drawImage`, `CameraDirectLookSystemUtil_handleLookInput`
и т.д.), отдельно править не надо — они тянут индекс/адрес из тех же таблиц.

## 2. Важно про текущее поведение при провале

В `SigManager::initialize()` и `OffsetProvider::initialize()` есть блок
`#ifndef __DEBUG__`: если хоть одна подпись не найдена — пишется crash-log и
процесс убивается через `__fastfail`, то есть клиент говорит сразу и всё.

**Но `__DEBUG__` сейчас определён всегда** (`CMakeLists.txt:13`,
`add_compile_definitions(__DEBUG__)` без условий — вторая, условная строка на
это не влияет). Значит этот fail-fast мёртв: ненайденная подпись просто
остаётся `0`, и клиент падает позже и в случайном месте.

Для обновления версии это неудобно. Рекомендую на время апдейта убрать
безусловную строку (`CMakeLists.txt:13`), тогда:
- **Debug-конфигурация** → печатает все ненайденные подписи и живёт дальше;
- **Release** → падает сразу со списком, а не через 5 минут в игре.

Строка в логе, которую надо искать:

```
[signatures] failed to find <ИмяПодписи>
[offsets]    failed to find <ИмяПоля>
```

## 3. Порядок работ

1. **Собрать Debug** (в нём fail-fast выключен по определению) и запустить игру.
2. Открыть лог и выписать **все** `failed to find ...` — их всегда видно разом.
3. Идти по списку сверху вниз: каждая подпись — это либо изменившийся
   пролог функции, либо сдвиг относительно якоря.
4. После сигнатур — **индексы и оффсеты**: сама подпись может находиться, а
   вот «3-й операнд» уже не то, что раньше. Признак: игра запускается, но
   конкретная фича делает чушь (телепорт в 0,0,0, пустой target и т.п.).
5. **ID контента**: руды в `OreMinerV2.hpp` (самый частый симптом — модуль
   «работает», но не находит ни одного блока), `PacketID`, `ComponentHashes`.
6. Прогнать ключевые фичи: `.help`, телепорт (`LastTP`, `InfiniteAura`),
   рендер (ESP/ClickGui), хуки пакетов (чат/атака).

Итераций обычно 2–3: первая сборка покажет основную пачку, после починки
вылезет вторая (то, что раньше падало раньше по цепочке).

## 4. Как снимать новые подписи (практика)

1. Открыть новый `Minecraft.Windows.exe` в IDA/Ghidra (по возможности с PDB —
   тогда функции ищутся по именам; без PDB — по уникальным строкам/xref).
2. Взять те же функции, что уже есть в `SigManager.hpp` (список имён там же).
3. Для каждой сформировать паттерн так же, как в существующих записях:
   - 8–20 байт начала функции (или участка вокруг нужного вызова);
   - **все относительные операнды (`E8`, `FF 15`, disp32) заменяются на `?`** —
     именно поэтому паттерны переживают версии;
   - проверить уникальность: если `hat::compile_signature<...>` находится
     больше одного раза, удлинить паттерн вправо.
4. Если паттерн ловит **вызов** функции, а не её начало — это `SigType::RefSig`
   и последний аргумент `offset` указывает, где относительно совпадения
   начинается сама функция (для `E8 rel32` это `1`).
5. `DEFINE_INDEX_FIELD(name, "…", index, OffsetType::Index)` — паттерн ловит
   инструкцию, а `index` говорит, какой по счёту операнд декодировать:
   - `OffsetType::Index` → из операнда берётся **номер в vtable**;
   - `OffsetType::FieldOffset` → **смещение поля** в объекте.

Ошибка тут не падает — просто берётся чужое значение, поэтому после апдейта
стоит перепроверить count/index у критичных записей (в файле уже есть
комментарии вида `// Also works on .40` — ориентируйтесь на них).

## 5. Что ускоряет апдейт

- Держать рядом dump'ы новой версии (`offsets_fixed_double_tab.txt`,
  `component_sizes.json` — они уже лежат в корне проекта в этом формате):
  чужой дамп = готовый список адресов структур и компонентов.
- Не переписывать `.cpp` — 99% работы в четырёх файлах:
  `SigManager.hpp`, `OffsetProvider.hpp`, `ComponentHashes.hpp`, ID-таблицы.
- Один раз настроить сбор подписи скриптом (IDA Python) вместо ручного
  копирования байтов.
