# Быстрая сборка Solstice (Windows / MSVC)

Коротко: **10 минут за одну правку `Arraylist.cpp` — это не «MSVC такой медленный», это
конкретные грабли в `CMakeLists.txt`.** Ниже — что именно тормозило, что я поменял и как
собирать теперь.

---

## 1. Почему было долго (по пунктам, всё проверено в этом репозитории)

1. **Ты запускал configure на каждую сборку** (`cmake -S . -B build ...`). Configure — это не
   «просто настройка»: он **перегенерирует `src/Utils/Resources.hpp` и `src/Utils/Resources.cpp`**
   через `file(WRITE ...)`, причём безусловно — даже если содержимое не изменилось. А
   `Resources.hpp` подключён так: `src/pch.hpp` → `Utils/Utils.hpp` → `Resources.hpp`.
   `pch.hpp` форсится во **все** единицы трансляции
   (`target_precompile_headers`). Итог: у каждого файла изменился mtime зависимости →
   MSVC пересобирает **весь проект** (299 файлов), а следом идёт полный LTCG-линк.
   Вот твои 10 минут за одну правку.
2. **`/GL` + `/LTCG` в Release.** `/GL` откладывает кодогенерацию на этап линковки, `/LTCG`
   линкует всё целиком. Это самый дорогой шаг сборки, и он повторяется при каждом билде.
3. **Unity-батч 8 файлов.** Правя один `.cpp`, ты пересобираешь 8 файлов (в них весь ImGui +
   SDK + модули, каждый файл тяжёлый).
4. **`generate_build_info` на каждый билд**: `git rev-parse`, `git log`, `git diff`, `whoami`,
   два вызова `powershell` (поиск Minecraft + версия). А если менялось число изменённых
   файлов — перезапись `build_info.h` → пересборка всех, кто его включает (`ModuleManager.cpp`,
   `UpdateForm.cpp`, `BuildInfoCommand.cpp`).
5. **Не было `/MP`** — компиляция внутри проекта не параллелилась (`-j` = `/m` помогает только
   между проектами, а «тяжёлый» тут один).

## 2. Как собирать теперь

### Вариант А — просто запустить bat (рекомендую)

```bat
dev.bat            :: быстрая итерация (build-dev)
dev.bat release    :: релизная сборка (build, как раньше)
```

Скрипт делает `configure` **только при первом запуске** (или когда менялся `CMakeLists.txt`),
дальше — чистая сборка. Дальше твой цикл — это просто повторный `dev.bat`.

### Вариант Б — пресеты CMake

```bat
cmake --preset dev          :: один раз
cmake --build --preset dev -j
```

### Вариант В — руками (то же, что пресет `dev`)

```bat
:: один раз:
cmake -S . -B build-dev -G "Visual Studio 17 2022" -A x64 -DSOLSTICE_FAST_DEV=ON

:: дальше ТОЛЬКО это (без повторного cmake -S . -B):
cmake --build build-dev --config Release --target Solstice -j
```

> Главное правило: **в цикле правка → сборка команда `cmake -S . -B ...` не запускается.**
> Это и было 80% твоих 10 минут.

## 3. Что такое `SOLSTICE_FAST_DEV`

Флаг `-DSOLSTICE_FAST_DEV=ON` (его включает `dev.bat` и пресет `dev`) делает:

| Что | Обычный Release | `SOLSTICE_FAST_DEV=ON` |
|---|---|---|
| `/GL` (compile) + `/LTCG` (link) | включены | **выключены** ← главный выигрыш |
| Линковка | `/INCREMENTAL:NO` | `/INCREMENTAL` |
| PDB | полный `/DEBUG` | `/DEBUG:FASTLINK` (быстрый) |
| `/MP` (параллельная компиляция) | включён | включён |
| Unity-батч | 8 файлов | 4 файла (правка одного файла пересобирает меньше) |
| `build_info.h` | генерируется на каждый билд | один раз на configure |
| Обновление зависимостей из git | на каждый configure | не трогает (`FETCHCONTENT_UPDATES_DISCONNECTED`) |
| Оптимизации `/O2 /Oi /Ob2 /Ot /Gy /Gw /MT /fp:fast ...` | включены | включены |

Плюс — независимо от флага — исправлены два генератора файлов: теперь `Resources.hpp`,
`Resources.cpp` и `build_info.h` **пишутся только при реальном изменении содержимого**
(и сравнение, и запись — в `CMakeLists.txt` / `GenerateBuildInfo.cmake`).
Поэтому даже если ты случайно снова запустишь configure — полной пересборки не будет.

**Что это значит на практике** (ориентиры, зависят от CPU/диска):

* правка одного `.cpp` (типа `Arraylist.cpp`): было ~10 мин → стало ~15–60 сек;
* правка общего заголовка (`pch.hpp`, `Module.hpp`): остаётся дорогой (~1–4 мин), но без LTCG;
* полная сборка с нуля: тоже быстрее за счёт `/MP` и отсутствия `/GL`.

Замерить у себя: MSBuild в конце пишет `Time Elapsed` — сравни `dev.bat` и `dev.bat release`.

## 4. Что ещё можно выжать (по убыванию эффекта)

1. **Исключения в Windows Defender** — реально режет время линковки (link.exe пишет
   десятки МБ DLL + PDB, антивирус это сканирует). PowerShell от админа:

   ```powershell
   Add-MpPreference -ExclusionPath "D:\путь\к\lmarena"
   Add-MpPreference -ExclusionPath "C:\Program Files\Microsoft Visual Studio\2022"
   Add-MpPreference -ExclusionProcess "cl.exe"
   Add-MpPreference -ExclusionProcess "link.exe"
   Add-MpPreference -ExclusionProcess "MSBuild.exe"
   ```

2. **Проект — на SSD, и НЕ в OneDrive/облачной папке.** Синхронизация `build`-каталога
   убивает сборку сильнее любого флага.
3. **Не трогать общие заголовки ради мелочей.** Пример: чтобы добавить аррейлисту пару полей
   анимации, я специально не расширял `Module.hpp`, а держу состояние в `Arraylist.cpp`.
   Если добавляешь поле в `Module.hpp` / `Settings.hpp` / `pch.hpp` — это пересборка почти всего.
4. **Диагностика «что пересобирается и почему»**:
   ```bat
   cmake --build build-dev --config Release --target Solstice -- -bl:build.binlog
   ```
   и открыть `build.binlog` в [MSBuild Structured Log Viewer](https://msbuildlog.com/) —
   видно построчно, какие файлы и из-за какой зависимости перекомпилируются.
   Быстрый вариант — в конце вывода: `-- -clp:PerformanceSummary`.
5. **Опционально, если хочется ещё 2–3×**: компилятор `clang-cl` + линкер `lld`
   (в установщике VS — компонент «C++ Clang tools for Windows»):
   ```bat
   cmake -S . -B build-clang -G "Visual Studio 17 2022" -A x64 -T ClangCL -DSOLSTICE_FAST_DEV=ON
   ```
   Это ускоряет и компиляцию, и линковку, но DLL надо тестировать в игре — код проекта
   написан под MSVC (`__forceinline`, `__int16`, `__declspec`), обычно clang-cl это ест,
   но не гарантирую 100%. Держи это как эксперимент, релиз собирай MSVC.
6. **Правишь визуалы (HUD/аррейлист)?** Компиляция вообще не нужна:
   `tools/arraylist-preview.html` — порт рендера 1:1, настройки и пресеты крутятся живьём.
   Сначала доводишь вид там, потом одной правкой переносишь в код.

## 5. Риски dev-профиля

* Нет `/LTCG` → код местами чуть медленнее (в игре обычно незаметно). **Релиз собирать через
  `dev.bat release`** или пресетом `release`.
* `/DEBUG:FASTLINK` → PDB ссылается на `.obj` файлы; стектрейсы из крешлога могут быть
  менее информативными. Нужны полные символы — собери release-профилем.
* `build_info.h` в dev-профиле обновляется только на configure, поэтому в команде,
  показывающей версию/изменённые файлы, могут быть слегка устаревшие данные.
  Это осознанная плата за то, что он не дёргает пересборку.

## 6. Мелочи, о которых стоит знать

* `src/CMakeLists.txt` — **мёртвая копия** корневого файла, она нигде не подключается
  (`add_subdirectory(src)` в корневом `CMakeLists.txt` нет). Правь флаги только в корневом
  `CMakeLists.txt`.
* Ресурсы (`resources/*.png|ttf|wav`) вшиваются через `ld -r -b binary` — это ~250 мелких
  вызовов, но они выполняются **только когда ресурс реально изменился**, так что на скорость
  обычной сборки не влияют.
* `build-dev/` и `build/` — это отдельные каталоги со своими кэшами; переключаться между
  профилями можно свободно, они не мешают друг другу (первый запуск в новом каталоге — полная сборка).
